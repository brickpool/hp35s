=head1 NAME

Parser::HPC - parse HP calculator assembler source code

=head1 SYNOPSIS

  use Parser::HPC;

  my $parser = Parser::HPC->new;

  my $program = $parser->from_string(<<'ASM');
  MACRO PUSH value
    value
    STO(I)
    DSE I
  ENDM

  %TITLE "Example"
  IDEAL
  P35S
  MODEL TINY

  STACK
    REGX SET 4

  DATASEG
    FORMULA EQU 'A+B'

  CODESEG
  start:
    LBL A
    PUSH 9.1
    EQN FORMULA
    GTO start
    RTN
  END start
  ASM

=head1 DESCRIPTION

C<Parser::HPC> is a recursive-descent, one-pass parser for HP calculator
assembler source code. It parses program headers, section selectors, assembler
directives, macro definitions and calls, labels, instructions, and calculator
literals.

The result is a normalized abstract syntax tree represented by Perl hashes,
arrays, and scalar values. Repeated source sections are combined by type,
macros are expanded at their call sites, and local labels are resolved before
the final AST is returned.

Only C<IDEAL> syntax, the C<P35S> calculator language, and the C<TINY> memory
model are currently supported. C<IDEAL> and C<P35S> are the initial parser
states. A C<MODEL TINY> directive is required in a complete program.

C<STACK>, C<DATASEG>, and C<CODESEG> select parsing contexts. They do not
represent distinct HP-35s address spaces. A new section selector ends the
preceding section. Explicit C<SEGMENT> and C<ENDS> syntax is not supported.

C<SET> assignments are accepted in C<STACK>, C<EQU> definitions in C<DATASEG>,
and executable calculator statements in C<CODESEG>.

=head1 ASSEMBLER GRAMMAR

=head2 Notation

The following grammar uses an EBNF-like notation:

  item          required item
  [ item ]      optional item
  { item }      zero or more repetitions
  item | item   alternatives
  "text"        literal keyword or punctuation

Whitespace and comments may occur where the parser permits token separation.
A comment begins with C<;> and continues to the end of the physical line.
Keywords and symbol names are matched case-insensitively unless the target
vocabulary defines a case-sensitive operation spelling.

The grammar describes the source structure. Calculator instruction and literal
vocabularies are provided by L<HP35s::Vocabulary> and are not repeated here.

=head2 Program

  program =
      header,
      { top-level-directive | section },
      end-directive ;

  header =
      { header-item } ;

  header-item =
        title-directive
      | mode-directive
      | language-directive
      | model-directive
      | display-directive
      | locals-directive
      | radix-directive
      | macro-definition ;

  top-level-directive =
        display-directive
      | locals-directive
      | radix-directive ;

  end-directive =
      "END", [ label-name ] ;

Header items may appear before the first section selector. Macro definitions
may therefore precede an explicit C<IDEAL> directive; C<IDEAL> is already the
default parser mode.

C<MODEL TINY> must be specified before the first section. C<END> may optionally
name an existing global label as the program start address. Input after C<END>
is ignored.

=head2 Header directives

  title-directive =
      "%TITLE", quoted-string ;

  mode-directive =
      "IDEAL" ;

  language-directive =
      "P35S" ;

  model-directive =
      "MODEL", "TINY" ;

  display-directive =
      "DISPLAY", quoted-string ;

  locals-directive =
        "LOCALS"
      | "NOLOCALS" ;

  radix-directive =
      "RADIX", ( "2" | "8" | "10" | "16" ) ;

These directives occupy one physical line apart from whitespace and a comment.
C<DISPLAY> emits its message as a parser warning. C<LOCALS>, C<NOLOCALS>, and
C<RADIX> change parser state for subsequent source.

=head2 Sections

  section =
        stack-section
      | data-section
      | code-section ;

  stack-section =
      "STACK",
      { stack-item } ;

  stack-item =
        stack-assignment
      | display-directive
      | locals-directive
      | radix-directive
      | macro-definition ;

  stack-assignment =
      register, "SET", number ;

  data-section =
      "DATASEG",
      { data-item } ;

  data-item =
        data-definition
      | display-directive
      | locals-directive
      | radix-directive
      | macro-definition ;

  data-definition =
      identifier, "EQU", ( number | quoted-string ) ;

  code-section =
      "CODESEG",
      { code-item } ;

  code-item =
        label-definition
      | macro-definition
      | macro-call
      | instruction
      | literal
      | display-directive
      | locals-directive
      | radix-directive ;

A section continues until another section selector or C<END> is encountered.
Repeated sections of the same type are combined in the returned AST.

=head2 Macros

  macro-definition =
      "MACRO", macro-name, [ macro-formals ],
      { local-declaration },
      { macro-source-line },
      "ENDM" ;

  macro-formals =
      identifier, { ",", identifier } ;

  local-declaration =
      "LOCAL", label-name, { ",", label-name } ;

  macro-call =
      macro-name, [ macro-actuals ] ;

  macro-actuals =
      macro-actual, { ",", macro-actual } ;

  macro-source-line =
      source-text-without-comment ;

A C<LOCAL> declaration is valid only before the first macro source line.
Macro bodies are preserved as source lines when the definition is parsed.
They are not validated as calculator code until the macro is called.

A macro actual is a source fragment. A comma separates actual arguments only
at the top level. Commas inside quoted strings or balanced C<(...)>, C<[...]>,
and C<{...}> groups remain part of the argument. Delimiters remain part of the
stored source fragment. For example:

  CALL 9.1,x<>?,"1, 2",[1,2]

contains four actual arguments:

  9.1
  x<>?
  "1, 2"
  [1,2]

When a macro is called, actual arguments are substituted for formal parameters
in the saved source lines. Quoted text in the macro body is left unchanged by
formal-parameter substitution. The expanded source is then parsed as ordinary
code. Syntax validation therefore occurs after substitution.

Macro calls may be nested. Expansion depth is limited so that direct or
indirect recursive macros fail with a parser error rather than recursing
without bound.

=head2 Labels

  label-definition =
      label-name, ":" ;

  label-name =
      global-label | local-label ;

  local-label =
      "@@", identifier-fragment ;

Label names are case-insensitive and are returned in canonical upper case.
Names beginning with a decimal digit are rejected as label definitions.
Calculator addresses such as C<A123> are not valid label definitions.

C<@@dddd> and C<??dddd>, where C<dddd> is exactly four decimal digits, are
reserved for parser-generated labels and cannot be used as source labels.

With C<LOCALS> enabled, C<@@NAME> denotes a local label. The parser assigns an
internal C<@@dddd> identity during AST preparation. A declaration and its
matching C<GTO>/C<XEQ> references receive the same identity. A new non-local
label starts a new local-label scope. Forward references are supported.

With C<NOLOCALS> enabled, an C<@@NAME> source label remains a normal global
label and is not rewritten.

Names declared by C<LOCAL> inside a macro use a separate C<??dddd> namespace.
Each macro expansion receives distinct internal identities, while every
reference to the same macro-local name within that expansion receives the same
identity.

=head1 MACRO PROCESSING

Macro processing is part of C<Parser::HPC>; no separate source preprocessor is
used.

For each macro call the parser:

=over 4

=item 1.

Binds actual source fragments to the macro's formal parameters.

=item 2.

Substitutes formal parameters in the saved macro source without rescanning
replacement text.

=item 3.

Parses the expanded source as a normal code block in the current parser state.

=item 4.

Assigns unique C<??dddd> identities to macro-local labels.

=item 5.

Inserts the expanded statements into the surrounding code statement stream.

=back

The current radix and C<LOCALS>/C<NOLOCALS> state at the call site apply while
the expanded source is parsed. Macro definitions and calls share the normal
global symbol table. A macro name therefore cannot also be used as a label,
equation, variable, opcode, or other symbol kind.

=head1 ABSTRACT SYNTAX TREE

=head2 Program node

C<parse> and C<from_string> return the normalized program AST:

  {
    language => $language,
    model    => $model,
    segments => [
      $segment,
      ...
    ],

    # Present only when specified by the source
    title => $title,

    # Present only when END specifies a start label
    startaddr => {
      type  => 'label',
      value => $label,
    },
  }

C<language> is currently C<P35S>. C<model> is currently C<0>, representing
C<TINY>. C<title> is optional. C<startaddr> is present only when C<END> names an
existing label.

C<segments> contains the combined stack, data, and code nodes. Directives that
only change parser state do not produce segment nodes.

=head2 Stack segment node

  {
    name        => 'STACK',
    type        => 'stack',
    assignments => {
      $register => {
        type  => 'register',
        value => $value,
      },
      ...
    },
  }

Assignments are keyed by register name. If a register is assigned more than
once, the later C<SET> value replaces the earlier value. Stack assignments do
not retain source order.

=head2 Data segment node

  {
    name        => '_DATA',
    type        => 'data',
    definitions => [
      {
        name  => $name,
        type  => 'equation',
        value => $value,
      },
      ...
    ],
  }

Definitions retain source order. Their values are parsed numbers or the
contents of quoted strings.

=head2 Code segment node

  {
    name       => '_TEXT',
    type       => 'code',
    statements => [
      $statement,
      ...
    ],
  }

Statements retain source order. Repeated C<CODESEG> sections are combined.
Internal parser directives used while resolving labels are removed before the
AST is returned.

=head3 Label statement

  {
    label => {
      name => $name,
    },
  }

The final label name is canonical upper case or a generated C<@@dddd> or
C<??dddd> identity. Intermediate parser classifications for ordinary,
local, and macro-local labels are not part of the returned AST contract.

=head3 Instruction statement

Without an operand:

  {
    instruction => {
      value => $mnemonic,
    },
  }

With an operand:

  {
    instruction => {
      value   => $mnemonic,
      operand => {
        type  => $type,
        value => $value,
      },
    },
  }

Operand C<type> may be:

=over 4

=item C<address>

A calculator address such as C<A001>.

=item C<label>

A global label or a resolved C<@@dddd>/C<??dddd> identity.

=item C<variable>

A direct or indirect calculator variable.

=item C<decimal>

A decimal integer operand for an instruction that accepts a numeric argument.

=item C<equation>

The name of an existing equation.

=item C<expression>

The contents of an inline quoted expression.

=back

The operand field is omitted for instructions without an operand.

=head3 Literal statement

  {
    literal => {
      kind  => $kind,
      value => $value,
    },
  }

Literal C<kind> may be C<constant>, C<vector>, C<complex>, C<binary>, C<octal>,
C<decimal>, or C<hex>.

The representation of C<value> depends on the recognized token. Consumers must
not assume that every numeric value uses the same Perl scalar representation.
For example, decimal integers may be numeric scalars while decimal floating
point values may retain their source spelling.

Unsuffixed non-decimal code literals receive a suffix in the returned value so
that the selected radix remains visible to AST consumers.

=head2 AST consumer notes

The AST represents parsed source structure rather than the calculator's final
program or memory layout. C<STACK>, C<DATASEG>, and C<CODESEG> are source
contexts, not separate HP-35s address spaces.

The AST does not contain calculated program addresses or a derived label index.
Labels remain individual statements. Address calculation and label indexing
are responsibilities of the AST consumer.

Consumers should inspect discriminating keys and fields rather than relying on
Perl scalar representation alone:

=over 4

=item *

A segment is identified by C<type>: C<stack>, C<data>, or C<code>.

=item *

A code statement contains C<label>, C<instruction>, or C<literal>.

=item *

An instruction operand is identified by its C<type>.

=item *

A literal is identified by its C<kind>.

=back

=head1 PARSER AND FRONTEND RESPONSIBILITIES

C<Parser::HPC> validates assembler syntax and produces a normalized AST.
The returned AST is intended as the input contract for assembler frontends.

The parser is responsible for:

=over 4

=item *

recognizing assembler syntax and symbols;

=item *

expanding macro calls;

=item *

resolving macro-local and scoped local labels;

=item *

normalizing repeated source sections;

=item *

returning finalized label and operand identities.

=back

The frontend is responsible for interpreting that AST for its target output.
This includes calculating program addresses, resolving target-specific output
positions, producing calculator source or listings, and applying output
formatting.

The frontend does not need to interpret macro syntax, C<LOCAL>,
C<LOCALS>/C<NOLOCALS>, or intermediate label types. Those constructs have
already been resolved before the AST is returned.

This separation allows alternative consumers to use the same parser AST
without reproducing assembler grammar or macro semantics.

=head1 CONSTRUCTOR

=head2 new

  my $parser = Parser::HPC->new(%args);

Creates a parser. Additional arguments are passed to the constructor inherited
from L<Parser::MGC>.

The initial parser state is:

  mode      IDEAL
  language  P35S
  model     TINY
  radix     10
  locals    enabled

A complete program must still contain C<MODEL TINY> before its first section.

=head1 METHODS

=head2 from_string

  my $program = $parser->from_string($source);

Parses a complete assembler source string and returns the normalized program
AST documented under L</ABSTRACT SYNTAX TREE>.

Macro definitions and calls are handled by C<Parser::HPC> during parsing.
Parsing failures are reported through the L<Parser::MGC> failure interface.

=head2 parse

  my $program = $parser->parse;

Parses the current input as a complete program and returns the normalized
program AST.

This method is the default top-level parser used by C<from_string>. Most callers
should use C<from_string> rather than invoking C<parse> directly.
