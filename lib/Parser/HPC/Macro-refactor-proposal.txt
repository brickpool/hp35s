Refactoring proposal: Remove Parser::HPC::Macro and move macro expansion to frontend

Context
- Repository: brickpool/hp35s
- Current macro implementation: lib/Parser/HPC/Macro.pm
- Current parser integration point: lib/Parser/HPC.pm (from_string pre-pass)

Decision summary
- Deprecate and remove Parser::HPC::Macro as a text preprocessor.
- Represent macro constructs directly in Parser::HPC AST.
- Perform macro expansion in a dedicated frontend phase operating on AST, not text.

Why this change
1) Two parsing models for one language fragment
- Today, macro syntax and behavior are implemented in a separate text parser and partially mirrored in Parser::HPC.
- This duplicates grammar knowledge and creates drift risk when language rules evolve.

2) String-level substitution is brittle
- Current expansion is line/text based and requires special-case handling for labels and address operands.
- Context-sensitive replacements become fragile and hard to reason about.

3) Scope semantics are not centralized
- Macro-only directives and normal directives are validated in different layers.
- Legality depends too much on call path instead of explicit parser scope state.

4) Error location and diagnosability
- Text pre-expansion weakens source-origin mapping for diagnostics.
- AST-level transformation can preserve origin/callsite metadata.

5) Scalability and extensibility
- PROC/MACRO-like scoped constructs are easier to extend with one grammar + one transform pipeline.

Current constraints and risks (as-is)
- Parser::HPC currently updates symbol tables and validates many things during parse (1-pass behavior).
- Macro bodies treated as normal code would currently trigger premature symbol conflicts.
- Existing behavior may rely on ordering and strict one-pass semantics.
- Some substitution behavior currently applies in text regions where semantic replacement may differ.

Strategic principles for refactor
1) Single source of truth for grammar
- Parser::HPC owns syntax recognition for macros and code statements.

2) Separation of concerns
- Parser: syntax + scope legality + minimal structural validation.
- Frontend: macro expansion, local renaming, argument substitution, post-expansion checks.

3) Explicit scope model
- Maintain scope state/stack (global, data, code, macro, proc).
- Directive legality is enforced by scope policy, not incidental call paths.

4) Deterministic symbol policy
- Macro names: global namespace (case-insensitive), redefinition policy explicit.
- LOCAL names: lexical to macro/proc definition, materialized uniquely per invocation at expansion.

5) Origin tracking
- Preserve source spans/origin info on AST nodes.
- During expansion, attach origin metadata (definition + callsite) for clear diagnostics.

Target architecture
A) Parser::HPC AST additions
- macro_def node:
  { type => 'macro_def', name => <ident>, params => [...], body => [...], locals => [...] }
- macro_call node:
  { type => 'macro_call', name => <ident>, args => [...] }
- local_decl node (macro/proc scope only):
  { type => 'local_decl', names => [...] }

B) Frontend macro expander module
- Suggested module: lib/Parser/HPC/MacroExpand.pm (or equivalent frontend namespace)
- Input: AST from Parser::HPC
- Output: expanded AST (macro_call nodes replaced with expanded statement nodes)
- Responsibilities:
  - bind formal params to actual args
  - generate unique local names (??NNNN)
  - substitute in label declarations and label/address references based on AST semantics
  - preserve/annotate origin metadata

C) Validation placement
- Parse-time: syntax, scope legality, header/body structure, argument count shape where possible.
- Expansion-time: semantic replacement and generated-name uniqueness.
- Post-expansion validation: symbol collisions, label/address consistency, instruction operand semantics.

Policy proposals (to be finalized)
1) Macro redefinition
- Recommended default: disallow; fail on duplicate macro name.

2) LOCAL directive legality
- Allowed only inside macro/proc scope.
- Outside scope: hard parse error.

3) Duplicate names
- Duplicate formal parameters: error.
- Duplicate LOCAL names within one definition: either deduplicate with warning or error; choose and document.
- LOCAL name equal to formal parameter: choose explicit rule (recommended: error for clarity).

4) Macro call before definition
- Keep one-pass-compatible behavior first: macro must be known before call.
- Optional future enhancement: pre-collect macro headers/definitions.

Migration plan (phased)
Phase 1: groundwork
- Add/standardize explicit scope state in Parser::HPC.
- Document directive scope/cardinality/effect matrix.

Phase 2: parser support for macro AST
- Parse MACRO...ENDM into macro_def nodes.
- Parse LOCAL in macro/proc scope into local_decl data.
- Parse macro calls as macro_call statements in code scope.

Phase 3: frontend expander
- Implement AST expansion pass with unique local generation (??NNNN).
- Add origin propagation (definition + callsite).

Phase 4: integration switch
- Remove Parser::HPC::Macro pre-pass from Parser::HPC::from_string.
- Run frontend expansion after parse and before final assembly stages.

Phase 5: cleanup and removal
- Deprecate then remove lib/Parser/HPC/Macro.pm.
- Update POD/docs and examples to new flow.

Testing strategy
1) Golden behavior tests
- Existing macro fixtures should produce identical effective expanded code/AST.

2) Scope legality tests
- LOCAL/ENDM outside macro/proc must fail with explicit message.

3) Name and substitution tests
- Parameter substitution correctness.
- Local uniqueness across multiple invocations (?? sequence).
- Case-insensitive matching where specified.

4) Diagnostics tests
- Errors should include accurate origin context (callsite + definition where relevant).

Non-goals (initial)
- No advanced macro language features beyond current semantics.
- No cross-file macro linking redesign in this step.

Compatibility considerations
- Preserve current accepted syntax as far as possible.
- Where behavior changes, document with migration notes and examples.

Recommended next actions
1) Finalize policy matrix (redefinition, duplicate LOCAL, LOCAL vs param, forward calls).
2) Add parser AST node scaffolding and scope plumbing.
3) Implement frontend expander in isolation with focused tests.
4) Switch integration path and remove text preprocessor dependency.
